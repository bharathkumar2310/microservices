# Microservices Real-Time Scenario Interview Questions
## Detailed Answers, Debugging Approach, Root Causes and Fixes

> A practical interview-preparation guide focused on production incidents and systematic debugging.

---

# 1. The Golden Debugging Framework

For almost every production issue, use this sequence:

1. **Confirm the problem**
    - What is failing?
    - Which service/API is affected?
    - When did it start?
    - Is every request affected or only some?

2. **Check monitoring**
    - Request rate
    - Error rate
    - P95/P99 latency
    - CPU
    - Memory
    - JVM/GC
    - Thread pools
    - Database metrics

3. **Check distributed tracing**
    - Follow one request across services.
    - Find exactly where the time is spent.

4. **Check logs**
    - Search using correlation ID / trace ID.
    - Identify exceptions and repeated retries.

5. **Identify the root cause**

6. **Fix and verify**

7. **Prevent recurrence**
    - Alerts
    - Monitoring
    - Capacity improvements
    - Timeouts/retries/circuit breakers
    - Tests and runbooks

# 2. API Suddenly Becomes Slow

## Interview Question

**Your API normally responds in 200 ms, but suddenly P95 latency becomes 5 seconds. How do you investigate?**

## Strong Interview Answer

First, I would confirm the scope of the issue. I would check whether all APIs are slow or only one endpoint.

Then I would check:

### Step 1: Traffic

- Has request volume increased?
- Is there a sudden traffic spike?
- Is one client sending excessive requests?

Metrics:

- Requests per second
- Requests per endpoint
- Active requests

### Step 2: Latency

I would compare:

- P50
- P95
- P99

Example:

- P50 = 200 ms
- P95 = 5 seconds
- P99 = 10 seconds

This means most requests are still reasonably fast, but some requests are experiencing severe delays.

### Step 3: CPU

If CPU is close to 100%, the application may be CPU saturated.

Possible causes:

- Infinite loop
- Expensive computation
- Serialization overhead
- Too much traffic
- Excessive garbage collection

### Step 4: JVM and GC

I would check:

- Heap usage
- GC frequency
- GC pause time
- Full GC

Frequent or long garbage collection pauses can directly increase API latency.

### Step 5: Thread Pools

I would check:

- Active threads
- Queue size
- Rejected tasks
- Thread states

If threads are waiting for a downstream service or database, the request queue can grow.

### Step 6: Database

I would check:

- Database query latency
- Slow queries
- Connection pool usage
- Locked queries

### Step 7: Distributed Trace

Finally, I would inspect a slow request trace.

Example:

```
Client
  |
Gateway - 20 ms
  |
Order Service - 50 ms
  |
Payment Service - 4.8 sec   <-- bottleneck
```

Then I would investigate the Payment Service.

## Possible Fixes

- Optimize slow SQL
- Add indexes
- Fix thread pool exhaustion
- Increase capacity if traffic increased
- Fix GC problems
- Add caching
- Add circuit breaker
- Tune downstream timeout

# 3. Connection Timeout vs Connection Refused vs Read Timeout

These are commonly asked interview questions.

## A. Connection Timeout

### Meaning

The client tries to establish a TCP connection, but does not receive a response before the connection timeout expires.

Example:

```
Service A
   |
   | ---- TCP connection request ---->
   |
   |          No response
   |
Timeout
```

### Possible Causes

1. Firewall silently drops packets
2. Security group blocks traffic
3. Network routing problem
4. Wrong IP address
5. Server is unreachable
6. Network partition

### How to Debug

From the calling server/container:

- Verify DNS resolution
- Verify IP
- Test connectivity to host and port
- Check routing
- Check firewall/security rules

Useful checks depend on the environment:

```
nslookup service-name
```

```
curl -v http://host:port
```

```
nc -vz host port
```

In Kubernetes:

```
kubectl get pods
kubectl get svc
kubectl get endpoints
```

### Fix

- Correct firewall rules
- Correct security group rules
- Fix routing
- Fix service IP/DNS configuration

---

## B. Connection Refused

### Meaning

The client reached the machine, but nothing is accepting connections on that port.

Example:

```
Client ---> Server
             |
             | Port 8080 closed
             |
        Connection Refused
```

### Common Causes

1. Application is down
2. Wrong port
3. Application is listening only on localhost
4. Container port mapping is incorrect
5. Service configuration is wrong

### Debugging

Check whether the application is running.

Check listening ports:

```
netstat
```

or:

```
ss -lntp
```

Check application logs.

Check:

```
server.port
```

For Docker:

- Container running?
- Correct port mapping?

For Kubernetes:

- Service targetPort correct?
- Pod listening on expected port?

### Fix

- Start application
- Correct port
- Correct container mapping
- Correct Kubernetes Service configuration

---

## C. Read Timeout

### Meaning

The connection was successfully established, but the server did not send a response within the configured read timeout.

Example:

```
Client ---- Connected ----> Server
Client <--- waiting --------
Client <--- waiting --------
Client <--- timeout --------
```

### Common Causes

1. Slow database
2. Slow downstream API
3. Thread pool exhaustion
4. Deadlock
5. Long-running processing
6. Server overload

### Debugging

Check distributed tracing.

Find where the request is spending time.

Check:

- SQL query duration
- Downstream API duration
- Thread dumps
- CPU
- Database connections

### Fix

Fix the actual bottleneck.

Do not simply increase the timeout unless the operation genuinely requires more time.

# 4. Service Suddenly Returns HTTP 500

## Interview Question

**Your production API suddenly starts returning 500 errors. What do you do?**

## Debugging Approach

### Step 1: Check Error Rate

Determine:

- Which endpoint?
- When did it start?
- What percentage of requests fail?

### Step 2: Check Recent Changes

Ask:

- Was there a deployment?
- Configuration change?
- Database change?
- Infrastructure change?

### Step 3: Check Logs

Search using:

- Trace ID
- Correlation ID
- Exception name

Examples:

```
NullPointerException
```

```
DataIntegrityViolationException
```

```
SQLException
```

```
OutOfMemoryError
```

### Step 4: Trace the Request

Determine whether the failure happens:

```
Gateway
   |
Service A
   |
Service B
   |
Database
```

### Step 5: Fix

Depending on root cause:

- Roll back bad deployment
- Fix configuration
- Fix database issue
- Increase capacity
- Fix application bug

# 5. Database Suddenly Becomes Slow

## Scenario

The API is slow, but CPU is normal.

## Investigation

Check database metrics:

- Query latency
- Active connections
- Connection pool usage
- Slow query log
- Locks
- CPU on database
- Disk I/O

## Common Root Causes

### Slow Query

Example:

```
SELECT * FROM orders WHERE customer_name = ?
```

If `customer_name` is frequently searched but not indexed, the database may perform a table scan.

### Fix

Create an appropriate index.

### Connection Pool Exhaustion

Example:

```
Maximum connections = 20
Active connections = 20
Waiting threads = 50
```

New requests wait for a database connection.

### Possible Causes

- Connections not returned
- Slow queries
- Too small pool

### Debugging

Check HikariCP metrics:

- Active connections
- Idle connections
- Pending connections

### Fix

First find why connections are exhausted.

Do not blindly increase the pool size.

# 6. Thread Pool Exhaustion

## Scenario

API latency increases and eventually requests start failing.

## What Happens?

Suppose:

```
Thread pool = 50 threads
```

Each request calls a slow downstream service.

All 50 threads become blocked waiting.

Then:

```
New requests
     |
     v
Request Queue
     |
Queue becomes full
     |
Requests rejected / timeout
```

## How to Debug

Check:

- Active threads
- Queue size
- Rejected task count

Take a thread dump.

Look for many threads in:

```
WAITING
```

or:

```
TIMED_WAITING
```

or blocked on the same downstream operation.

## Fix

- Fix downstream dependency
- Configure timeout
- Configure circuit breaker
- Use bulkheads
- Tune thread pools carefully

# 7. CPU Suddenly Reaches 100%

## Investigation

### Step 1

Check whether traffic increased.

### Step 2

Check JVM metrics.

### Step 3

Check GC.

Frequent GC can consume significant CPU.

### Step 4

Take thread dump.

Look for:

- RUNNABLE threads
- Same method repeatedly consuming CPU

### Step 5

Use CPU profiling if necessary.

## Common Causes

- Infinite loop
- Expensive JSON serialization
- Large data processing
- High traffic
- GC pressure
- Encryption/compression overhead

# 8. Memory Keeps Increasing

## Possible Causes

1. Memory leak
2. Large cache
3. Large collections
4. Requests retained in memory
5. Static collections
6. ThreadLocal not cleaned
7. Large objects

## Debugging

Check heap trend.

Take heap dumps.

Compare:

- Dominator tree
- Retained size
- Object counts

Ask:

**Which objects are continuously growing?**

Example:

```
HashMap
   |
   +-- 10 million objects
```

Then find why objects are not being released.

# 9. OutOfMemoryError

## Strong Interview Approach

First identify the exact type.

Examples:

```
Java heap space
```

```
GC overhead limit exceeded
```

```
Direct buffer memory
```

Each indicates a different problem.

## Debugging

1. Check application logs
2. Check heap usage trend
3. Check GC
4. Capture heap dump
5. Analyze largest retained objects

## Important

Increasing heap is not always the correct fix.

If there is a memory leak, increasing heap only delays the failure.

# 12. Service Discovery Issue

## Scenario

A service is running, but other services cannot discover it.

## Investigation

Check:

1. Is the service registered?
2. Are heartbeats working?
3. Is the service marked healthy?
4. Are clients using stale cache?
5. Is the hostname/IP correct?

## Common Problem

The service registers with an unreachable IP.

Example:

```
Service Registry:
Payment -> 10.0.0.5:8080
```

But other services cannot reach `10.0.0.5`.

## Fix

Correct service registration configuration.

# 13. Retry Storm

## Scenario

A downstream service becomes slow.

Clients retry:

```
100 requests
   |
Each retries 3 times
   |
400 total requests
```

The overloaded service receives even more traffic.

This is called a **retry storm**.

## Prevention

Use:

- Limited retries
- Exponential backoff
- Jitter
- Circuit breaker

Do not retry every error.

# 14. Circuit Breaker Opens

## Scenario

Service B is failing.

Without circuit breaker:

```
Service A threads
      |
      v
Service B (slow/down)
```

Threads keep waiting.

With circuit breaker:

```
Failures exceed threshold
        |
Circuit opens
        |
Fail fast
```

## Debugging

Check:

- Failure rate
- Slow call rate
- Circuit breaker state

States:

- CLOSED
- OPEN
- HALF_OPEN

# 15. Message Is Processed Twice in Kafka

## Important Interview Concept

Kafka consumers should generally be designed to be **idempotent**.

Example:

```
Payment event
```

is delivered twice.

Without idempotency:

```
Charge customer twice
```

## Solution

Store a unique event ID.

Example:

```
event_id = 123
```

Before processing:

```
Was event 123 already processed?
```

If yes:

```
Ignore duplicate
```

Possible techniques:

- Unique database constraint
- Processed event table
- Idempotency key

# 16. Kafka Consumer Lag Suddenly Increases

## Meaning

Messages are arriving faster than consumers can process them.

## Investigation

Check:

- Consumer lag
- Consumer processing time
- Consumer errors
- Number of partitions
- Number of consumers

## Common Causes

1. Consumer processing is slow
2. Database is slow
3. Consumer crashed
4. Not enough consumer instances
5. Poison message repeatedly fails

## Fix

- Optimize processing
- Scale consumers
- Increase partitions if appropriate
- Fix poison messages
- Use retry/DLT strategy

---

# 17. Poison Message in Kafka

## Scenario

One message always fails processing.

Consumer repeatedly processes it.

## Solution

Use retry strategy:

```
Main Topic
    |
Failure
    v
Retry Topic
    |
Failure again
    v
DLT
```

Then investigate the failed message separately.

## 502 Bad Gateway

Usually means gateway/proxy received an invalid response from upstream.

Possible causes:

- Upstream service crashed
- Connection problem
- Invalid upstream response

## 504 Gateway Timeout

Gateway waited too long for upstream service.

Possible causes:

- Slow service
- Slow database
- Downstream dependency delay

## Debugging

Use distributed tracing:

```
Client
 |
Gateway
 |
Order Service
 |
Database
```

Find where time is spent.

# 19. One Service Is Healthy but Requests Fail

Health status alone does not guarantee the service can handle real traffic.

Example:

```
/health -> UP
```

But:

- Thread pool exhausted
- Database unavailable
- Downstream dependency failing

## Better Approach

Use appropriate health checks:

- Liveness
- Readiness

### Liveness

Is the application process alive?

### Readiness

Is the application ready to receive traffic?

## Investigation

# 22. How to Answer Any Production Debugging Question

Use this interview structure:

> First, I would confirm the scope and impact of the issue. Then I would check monitoring metrics such as traffic, error rate, P95/P99 latency, CPU, memory, JVM GC, thread pools, and database metrics. After identifying the affected component, I would use distributed tracing to locate where the request spends time. Then I would correlate the trace with application logs using the trace ID. After identifying the root cause, I would apply the appropriate fix, verify the metrics return to normal, and finally add monitoring or preventive mechanisms to avoid recurrence.

| 504 | Upstream latency | Slow downstream |

# Final Interview Tip

Do not answer production debugging questions by immediately saying:

> "I will restart the service."

A strong engineer first:

**Observes -> Measures -> Traces -> Correlates -> Identifies root cause -> Fixes -> Verifies -> Prevents recurrence**

That structured approach is what interviewers usually look for in real-world microservices troubleshooting questions.
