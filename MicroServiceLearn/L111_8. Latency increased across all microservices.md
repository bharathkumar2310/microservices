Scenario


        "If latency increases across multiple microservices at approximately the same time, 
        I first look for a common cause rather than debugging each service independently.
        I would first confirm the latency increase using P50, P95 and P99 and check whether traffic or concurrency increased. 
        Then I would check the API gateway/load balancer, infrastructure and node health, and application CPU, memory, GC and thread pools. Since multiple services are affected,
        I would especially investigate shared dependencies such as the database, Redis, Kafka, authentication or other common downstream services. 
        I would also check DB and HTTP connection pools because the dependency itself can look healthy while applications are waiting for connections. 
        Finally, I would use distributed tracing to compare a healthy request with a slow request and identify where the additional latency is being introduced.
        Once I identify the common bottleneck, I would fix or mitigate that component and verify that P95/P99 latency returns to normal."

Suppose your architecture is:

                    Client
                       |
                       v
                API Gateway / LB
                       |
          ┌────────────┼────────────┐
          ↓            ↓            ↓
      Service A    Service B    Service C
          |            |            |
          └────────────┼────────────┘
                       ↓
              Shared Dependencies
              ┌────────┼─────────┐
              ↓        ↓         ↓
             DB      Redis     Kafka

Suddenly:

    Service A P95: 200ms → 2s
    Service B P95: 300ms → 3s
    Service C P95: 150ms → 2.5s

The first question should be:

    What do A, B and C have in common?


What are the "shared things"?

Start with just these:

                      ┌── Service A
                      │
    Client → Gateway ─┼── Service B
    │
    └── Service C
    │
    ↓
    Database
    
    There are two types of things to look for.

1. Shared things BEFORE the microservices
    
       Client
       ↓
       Load Balancer
       ↓
       Gateway
       ↓
       A / B / C

        If the Load Balancer or Gateway has a problem, many services can become slow.

2. Shared things USED BY the microservices

            ┌→ A ─┐
            │     │
            ├→ B ─┼→ Database
            │     │
            └→ C ─┘

       If the Database is slow, A, B and C can all become slow.

        Same idea with a shared Redis, authentication service, etc.

So your answer at this stage should be

    "Since latency increased across all microservices, I wouldn't investigate each microservice independently first. I would identify the components that are common to all of them. I would check the common components in the request path, such as the load balancer and gateway, and then look for shared dependencies such as the database, Redis, authentication service, or network. Once I identify which shared component is showing increased latency, I would investigate that component further."

Step 1 — Confirm that all services are actually affected

    Don't immediately assume it.

Open your monitoring system and look at:

    Service A → P95/P99
    Service B → P95/P99
    Service C → P95/P99
    Service D → P95/P99

For example:

        Service	Before	Current
        A	200 ms	2 sec
        B	150 ms	1.8 sec
        C	300 ms	3 sec
        D	250 ms	2.5 sec

Then check the time of increase.

If:

    10:00 → normal
    10:05 → A ↑
    10:05 → B ↑
    10:05 → C ↑
    10:05 → D ↑

that's a very strong clue.

You should ask:

    What changed around 10:05?

Step 2 — Check traffic first

    Go to your API/Gateway metrics.

Look at:

    Request rate / RPS
    Request count
    Concurrent requests
    Retries

For example:

        Before:
        RPS = 1,000
        
        At incident:
        RPS = 10,000

Now you have a possible explanation.

    All services may be slow because traffic increased 10×.
    
    But don't stop there.
    
    You need to find which component is getting saturated because of that traffic.

Step 4 — Check whether all services are on the same infrastructure

This is extremely important.

Suppose:

Service A → Node 1
Service B → Node 1
Service C → Node 1

If Node 1 has a problem:

Node 1 CPU = 95%
Node 1 memory pressure
Node 1 disk I/O high
Node 1 network problems

then all three services may become slow.

Check:

Kubernetes node CPU
Node memory
Disk I/O
Network
Container throttling
Pod CPU throttling
Pod restarts
OOM events
Example
Service A pod → Node 1
Service B pod → Node 1
Service C pod → Node 1

Node 1
CPU = 98%
↓
All pods affected
↓
All services latency ↑

So don't only look at individual service CPU.

Step 5 — Check service CPU and memory

Now check every service.

For example:

Metric	A	B	C
CPU	40%	35%	45%
Memory	Normal	Normal	Normal
Latency	High	High	High

If all services have normal CPU/memory, that's another clue.

It suggests:

The problem may be something they're waiting for.

Step 8 — Check DB connection pools

This is slightly different from checking DB health.

Suppose MySQL says:

DB CPU = 40%
DB latency = 20 ms

Looks healthy.

But Service A has:

Hikari:
maximumPoolSize = 20
active = 20
idle = 0
pending = 100

Then requests are waiting for connections.

So:

Application
↓
Need DB connection
↓
Pool has no connection
↓
Wait
↓
Latency ↑

And the DB itself might still look healthy.

This is a very important interview point.

Step 11 — Check distributed tracing

This is probably the most powerful step.

Take one slow request from Service A.

Example:

Request
|
+-- Gateway        20 ms
|
+-- Service A      30 ms
|
+-- Redis          20 ms
|
+-- DB             50 ms
|
+-- Service Auth   2.8 sec

Now you know:

Service A isn't actually spending 3 seconds processing the request. It's waiting for Auth.

Then take a slow request from B:

Gateway        20 ms
Service B      40 ms
Redis          10 ms
Auth           2.7 sec

And C:

Gateway        20 ms
Service C      30 ms
DB             50 ms
Auth           2.8 sec

Now the common dependency is obvious:

                Auth Service
               ↑     ↑     ↑
               |     |     |
               A     B     C

          Auth latency = 2.8 sec
Step 12 — Compare healthy and unhealthy traces

This is one of the best debugging techniques.

Healthy
Gateway      10 ms
Service A    30 ms
DB           50 ms
Redis        10 ms
Auth         20 ms

Total        ~120 ms
Slow
Gateway      10 ms
Service A    30 ms
DB           50 ms
Redis        10 ms
Auth         2800 ms

Total        ~2900 ms

The difference immediately points toward Auth.

Step 17 — Check retries

This is a very important distributed-system cause.

Suppose Service B becomes slightly slow.

Then:

A → B
timeout
retry

A → B
timeout
retry

Now traffic to B increases.

Then B becomes even slower.

B slow
↓
A retries
↓
B receives more traffic
↓
B becomes slower
↓
More retries
↓
System-wide latency increases

This is a retry storm.

Check:

Retry count
Retry rate
Timeout count
Circuit breaker state
Request amplification
