# Problem

Service A reports that it "cannot connect" to Service B. That phrase is not a diagnosis. It may mean DNS did not return an IP, TCP did not open, TLS rejected identity, HTTP returned an error, or HTTP connected but no response arrived before a deadline.

The safe investigation order is:

```text
DNS name -> IP route -> TCP socket -> TLS session -> HTTP request -> HTTP response
NXDOMAIN     no route    refused       bad SAN       4xx/5xx        read timeout
                         timeout       bad CA
```

A refusal is a fast TCP rejection. A connect timeout is an incomplete TCP handshake. A TLS error happens after TCP but before HTTP. A read timeout means the request was sent on an established connection. A 502/503/504 is an HTTP response, often generated by a gateway, so its generator and product subreason matter.

# Production Situation

At `2026-09-13T09:14:22Z`, Order Service A `order-a-4.18.2-k2m5q`, zone `eu-west-1b`, calls Inventory Service B route `POST /v1/inventory/reservations`.

* Request ID: `ord-7f93c2`
* Trace ID: `01f92f3577b34da6a3ce929d0e0e0001`
* A version: `4.18.2`
* Destination: `inventory-v2.internal:8443`
* Resolved target: `10.42.7.18`, instance `inventory-b-7.5-r8x2p`
* Normal: 220 requests/s, 99.95% success, p95 135 ms, p99 178 ms
* Abnormal: 58% success, 92 failures/s, p99 190 ms for successes
* A CPU/heap: 33%/57%; B CPU/heap: 34%/56%
* Failure: `SSLPeerUnverifiedException: no SAN matching inventory-v2.internal`

Low CPU does not make the path healthy. Fast successful requests also hide the failed population, so success and failure are separated.

# Architecture

```text
Customer
   |
   v
Order A 4.18.2 (Service A)
   |
   +-- DNS inventory-v2.internal -> 10.42.7.18
   +-- TCP :8443
   +-- TLS SNI inventory-v2.internal   X hostname validation
   |
   v
Envoy gateway/mesh
   |
   v
Inventory B 7.5 (Service B) -> PostgreSQL
```

The direct path is A -> B. The gateway path is A -> gateway -> B and has two separate DNS/TCP/TLS boundaries. A direct success does not prove the gateway path because SNI, identity, routing, protocol, and target selection can differ.

# What I Check FIRST

1. **Exact failure and time.** WHAT: preserve the deepest exception, UTC start, route, request/trace IDs, timeout phase, source and target. WHY: "cannot connect" spans several layers. LOOK FOR: a phase-specific error such as NXDOMAIN, refused, connect timeout, TLS, status, or read timeout.
2. **Blast radius.** WHAT: split errors by route, source version, target, instance, zone, new/reused connection, and direct/gateway path. WHY: a 42% failure can be one revision or connection population. LOOK FOR: a dimension that predicts failure.
3. **Adjacent boundary rates.** WHAT: compare A outbound attempts, gateway receives/upstream attempts, and B accepts. WHY: the first count mismatch is the last known good boundary. LOOK FOR: 220/s from A but zero matching B accepts.
4. **Phase latency.** WHAT: inspect DNS, connect, TLS, time-to-first-byte, and total. WHY: total latency alone hides the failed layer. LOOK FOR: DNS 1 ms, TCP 7 ms, TLS error 10 ms.
5. **Recent change.** WHAT: overlay deploy/config/certificate/network changes. WHY: change correlation directs comparison but is not proof. LOOK FOR: revision `cfg-a-883` immediately before the first failure.

# Step-by-Step Investigation

### Step 1 - Make the symptom testable

* **What I check:** one failed and one matched successful call from the same minute.
* **Why:** matched evidence controls route, payload class, identity, version, and traffic.
* **Example:** query telemetry for request `ord-7f93c2` and trace `01f92f3577b34da6a3ce929d0e0e0001`.
* **Expected result:** normal call has all phases and B returns 201 in 142 ms.
* **Bad result:** failed call ends with TLS exception before any HTTP status.
* **Meaning:** a secure session was not established; B application code did not handle it.
* **Next branch:** if no IP exists go to DNS; if connect failed go to TCP; here inspect TLS.

### Step 2 - Resolve in A's real network context

* **What I check:** FQDN, resolver, answer, TTL, lookup duration, and selected IP.
* **Why:** laptop DNS may use a different view and cache.
* **Example:** `Resolve-DnsName inventory-v2.internal -DnsOnly`.
* **Expected result:** `NOERROR`, `10.42.7.18`, TTL 30, under 10 ms.
* **Bad result:** NXDOMAIN means absent in that resolver view; SERVFAIL means resolution could not complete; timeout means no timely resolver response.
* **Meaning:** without an IP no TCP attempt is possible.
* **Next branch:** repair record/view/forwarder if bad; otherwise retain the IP and test its port.

### Step 3 - Prove one TCP handshake

* **What I check:** exact IP and port from the affected A pod.
* **Why:** DNS success proves no listener, firewall, or route.
* **Example:** `Test-NetConnection 10.42.7.18 -Port 8443`.
* **Expected result:** `TcpTestSucceeded : True` in about 7 ms.
* **Bad result:** fast false/refused selects listener or port; a bounded wait selects drop, route, policy, or reverse path.
* **Meaning:** this incident passes TCP, so increasing connect timeout is irrelevant.
* **Next branch:** test TLS with the exact SNI and trust used by A.

### Step 4 - Inspect the TLS identity

* **What I check:** SNI, presented SANs, issuer chain, expiry, protocol, client certificate, and A trust store.
* **Why:** TCP reachability does not authenticate the peer.
* **Example:** compare handshakes with SNI `inventory-v2.internal` and `inventory.internal`.
* **Expected result:** trusted chain and SAN matching the requested name.
* **Bad result:** new name reports hostname mismatch while old name reports `Verification: OK`.
* **Meaning:** A rejects B before sending HTTP.
* **Next branch:** compare effective configuration and certificate rotation, not just source control.

### Step 5 - Establish the HTTP/gateway boundary

* **What I check:** response presence, `server` header, gateway ID, Envoy response flags, upstream reason, and B access count.
* **Why:** 502/503/504 are generated somewhere.
* **Expected result:** a valid HTTP response has a generator and matching server/access event.
* **Bad result:** no HTTP status, no gateway upstream request, and no B access log.
* **Meaning:** the failure precedes HTTP.
* **Next branch:** for Envoy, 503 `UF` selects upstream connection/TLS failure, 503 `UH` selects no healthy upstream, and 504 `UT` selects upstream request timeout. An NGINX 502 requires its own error-log reason.

### Step 6 - Compare effective change state

* **What I check:** configuration hash, destination name, trust version, image, zone, and connection reuse on failed versus good A instances.
* **Why:** intended Git config may differ from loaded runtime config.
* **Expected result:** all instances use `inventory.internal`.
* **Bad result:** only revision `cfg-a-883` uses `inventory-v2.internal`.
* **Meaning:** the scope and onset follow a concrete SNI change.
* **Next branch:** reproduce safely once, preserve evidence, then roll back that revision.

### Step 7 - Eliminate false leads

* **What I check:** B CPU, GC, queues, thread pool, HTTP pool, DB pool, and dependency latency.
* **Why:** they confirm whether calls reached application work.
* **Expected result:** these remain at baseline because failures stop at TLS.
* **Bad result:** a B span and elevated queue/pool metrics would contradict a purely pre-B failure.
* **Meaning:** normal B resources support, but do not alone prove, the TLS conclusion.
* **Next branch:** follow any B child if present; otherwise close the causal chain with recovery.

### Result branches for the same "cannot connect" report

| Observed result | What it proves | What it does not prove | Exact next check |
|---|---|---|---|
| `NXDOMAIN` in A's pod | That resolver view has no name | The record is absent from every DNS view | Query the authoritative/private zone and compare A's resolver with a known-good consumer |
| `SERVFAIL` after 2 s | Resolution could not complete | B is unavailable | Test control zones through the same resolver, then inspect forwarder latency and route |
| DNS returns an unexpected IP | A can resolve a name, but target correctness is suspect | The unexpected target is unreachable | Reconcile TTL/address with registry, EndpointSlice, and owner inventory |
| TCP refusal in 2 ms | A reached something that actively rejected the port | The Java process is necessarily stopped | Inspect destination listener, bind address, target port, sidecar, and lifecycle |
| TCP connect expires at 5 s | The handshake did not complete in A's budget | Which firewall, route, or policy dropped it | Compare old/new sources, retransmits, flow action, destination SYN, and reverse path |
| TCP succeeds; hostname mismatch | A reached a TLS peer whose identity does not match SNI | The certificate is expired or untrusted | Compare SAN with effective SNI and a matched good handshake |
| TCP succeeds; PKIX failure | The JVM cannot build a trusted chain | B sent the wrong hostname certificate | Inspect presented chain and A's loaded trust hash |
| HTTP 401 or 403 | DNS, TCP, TLS, and HTTP responder were reached | The caller is authorized or business path works | Identify generator and inspect sanitized identity/authorization decision |
| Envoy 503 `UF` | Envoy could not establish/use its upstream connection, including upstream TLS | Whether refusal, timeout, reset, or TLS caused it | Read `upstream_transport_failure_reason` and upstream phase metrics |
| NGINX 502 with upstream error | NGINX could not obtain a usable upstream response | Whether connect, premature close, or protocol caused it | Read the exact NGINX error and upstream timing fields |
| Envoy 503 `UH` | This Envoy had no eligible upstream | B processes are all down | Compare health reasons, probe contract, EndpointSlice, and direct equivalent |
| Envoy 504 `UT` | Envoy's upstream request deadline expired | The gateway itself is slow | Compare upstream connect with response time, then open B's longest child |
| Client read timeout | A sent work and waited beyond its local response budget | DB is slow | Confirm B acceptance and separate queue, pool acquisition, query, lock, and external spans |

### Failure and control evidence set

For the failed request I record `resolved_ip=10.42.7.18`, `connect_ms=7`,
`sni=inventory-v2.internal`, `tls_ms=10`, and `http_status=none`.

For a matched success I record the same source version, zone, route, identity,
payload class, and minute, changing only the destination configuration.

The successful control uses `sni=inventory.internal`, completes TLS in 14 ms,
reaches B instance `inventory-b-7.5-r8x2p`, and returns 201 in 142 ms.

If both SNI values fail, the hostname-only explanation is incomplete.

If both succeed from `openssl` but Java fails, I compare trust stores,
hostname-verification behavior, proxy use, and client-certificate configuration.

If Java succeeds outside the pod but fails inside it, I compare mounted trust,
sidecar interception, DNS view, and effective environment rather than code.

If a gateway path succeeds while direct fails, I identify which component
terminates TLS and which trust/SNI/client identity each hop uses.

If direct succeeds while gateway fails, I reproduce from the gateway's context;
an A-pod curl is not an equivalent gateway-origin test.

### Spring client interpretation

Feign may wrap this event in `RetryableException`; I inspect its deepest cause
before deciding it is retryable.

WebClient/Reactor Netty can report a handshake exception from the connection
provider; pool acquisition, connect, and response timers must remain separate.

RestTemplate may expose `ResourceAccessException`; the nested
`SSLPeerUnverifiedException` is the phase-defining evidence.

No client library changes the layer order. A retry policy must reject
certificate-validation failures because another attempt with the same SNI and
trust produces the same result.

| Metric | High / low / flat interpretation | Split and change interpretation |
|---|---|---|
| Business success | Low means customer impact; high health-check success can coexist | Split route/region; drop after `cfg-a-883` implicates changed population |
| A request rate | High can cause capacity pressure; flat rejects demand spike | Split version/zone so fleet average does not hide scope |
| DNS error/duration | High NXDOMAIN/SERVFAIL locates failure before IP; low here clears this sample | Per resolver/name; after DNS change suggests view/forwarder |
| TCP connect error/duration | Fast refusal differs from high timeout plateau; low 7 ms means handshake succeeds | Per target/source/zone; after policy change suggests path |
| TLS failures/handshake | High reason=`hostname_mismatch` is decisive layer evidence | Split SNI/SAN/config; after cert/config rollout is strong correlation |
| A outbound vs B accepted | A high and B flat means work stopped before B or telemetry is missing | Per target and route; corroborate with access logs |
| p50/p95/p99/max | Low success latency can coexist with many fast failures | Plot successful and failed populations; avoid percentile without counts |
| Retry attempts/request | High amplifies load; 1.00 means no amplification | Per exception; deterministic TLS errors must not retry |
| CPU/heap/GC | High could delay work; low/flat does not prove health | Per instance/version; unchanged B values fit pre-B stop |
| Circuit breaker | Open means protection reacted, not root cause | Split destination/caller; inspect trigger before changing threshold |

# Distributed Trace Investigation

```text
traceId=01f92f3577b34da6a3ce929d0e0e0001
Order A server                         63ms span=a001
  Inventory HTTP client               18ms span=a002 ERROR
    dns.lookup                         1ms span=a003
    tcp.connect                        7ms span=a004
    tls.handshake                     10ms span=a005 ERROR hostname_mismatch
  [no gateway HTTP span]
  [no Inventory B server span]
```

The parent/child waterfall says DNS and TCP completed and TLS failed. I inspect `server.address`, `server.port`, SNI, target, instance, version, zone, attempt, connection reuse, and deadline.

A missing B child can mean pre-B failure, broken context propagation, unsampled B trace, exporter loss, or instrumentation gap. I verify trace sampling decisions and search B access logs by request ID before claiming B never received it. A blank duration is not automatically network latency.

# Root Cause

`cfg-a-883` changed A's SNI from `inventory.internal` to `inventory-v2.internal`, but B's certificate SAN contained only `inventory.internal`.

```text
config rollout
-> new SNI
-> DNS returns valid B IP
-> TCP opens
-> B presents trusted certificate with wrong hostname
-> A rejects identity before HTTP
-> 92 calls/s fail
-> reservation success falls to 58%
```

Every arrow has evidence: rollout annotation, loaded hash, DNS/TCP spans, certificate inspection, missing HTTP/B span, and aligned customer metric.

# Fix

**Immediate mitigation:** preserve failed/good evidence, pause rollout, and roll back only `cfg-a-883`. Confirm old-path capacity before shifting traffic. Do not add retries or extend timeouts for deterministic identity failure.

**Root cause correction:** issue an overlapping certificate containing the approved DNS identity or restore the contractual hostname. Align gateway SNI, service discovery, certificate SAN, and Java trust configuration.

**Permanent fix:** validate SAN/SNI/trust from the caller and gateway in canary tests; stage certificate rotation with overlap; report effective config hashes; fail deployment safely when hostname contracts disagree.

# Verification

Before: business success 58%, TLS failures 92/s, B accepted only 128/s, p99 successful call 178 ms.

After: business success 99.97%, TLS failures 0/s, B accepts 220/s, p99 171 ms, attempts/request 1.00 for 30 minutes. Calls from each A version and zone succeed through direct and gateway paths. A controlled reservation commits once and reconciliation shows no orphan or duplicate.

These numbers prove both technical boundary recovery and the customer outcome; a green `/health` alone would not.

# Prevention

* Alert on TLS failures by reason/SNI and on A-attempt versus B-accept mismatch.
* Alert 30/14/7 days before certificate expiry, but also test SAN and trust.
* Runbook: preserve IDs/config, DNS -> TCP -> TLS -> HTTP branches, direct/gateway comparison, rollback owner, numeric close criteria.
* Contract tests verify DNS name, port, SNI, SAN, mTLS identity, and supported protocol.
* Canary from every zone uses the real gateway and a non-destructive business synthetic.
* Deployment policy checks effective config equality and prevents retry on certificate validation errors.

# Interview Answer

### What I would say in an interview

I first translate "cannot connect" into a layer. Here A had normal DNS and a 7 ms TCP connect, but TLS failed with a hostname mismatch and B received no HTTP request. The failure followed config revision `cfg-a-883`, whose SNI was absent from B's certificate SAN. I preserved a failed and successful trace, rolled back that revision, then aligned the certificate and service name. I verified zero TLS errors, matching A/B request counts, business success above 99.9%, and no retry amplification for 30 minutes.

### Common interviewer traps

Do not start by restarting B, treat ping as HTTP proof, trust a laptop test, or increase timeouts. Do not call a recent deploy the root cause without showing its mechanism. A missing B span needs sampling and access-log corroboration.

### Quick memory flow

Symptom -> scope -> DNS -> IP/TCP -> TLS -> HTTP/generator -> trace -> correlated logs/config -> mitigate -> fix -> business verification.

# Interview Follow-up Questions

1. **Why is DNS success insufficient?** It returns an address; it proves neither route, listener, TLS, nor HTTP.
2. **Refused versus connect timeout?** Refused is an active fast rejection; timeout means the handshake did not complete within budget.
3. **Why no B span?** Failure may precede B, but sampling and propagation must be checked.
4. **Can I disable certificate validation?** No; that removes peer authentication and creates a security defect.
5. **Why can old connections still work?** Existing TLS sessions may remain pooled while new handshakes use the changed SNI.
6. **What does a 502 prove?** Only that an HTTP component returned 502; identify the generator and product subreason.
7. **Feign/WebClient relevance?** Capture the deepest cause and configure distinct connect/read deadlines; the client library does not change the network layers.
8. **Why verify business outcome?** Technical recovery can still leave duplicates, late writes, or semantic failure.
